# План реализации спецификации PyBot-ITAcadem (сентябрь 2026)

**Источник требований:** `PyBot-ITAcadem — спецификация изменений (сентябрь 2026).md`, согласованная 27.09.2026.
**Назначение:** план реализации по независимым feature-веткам и PR.
**Статус:** план; перед реализацией завершить T0 и разобраться с незакоммиченными изменениями в рабочем дереве.

## Как трактовать спецификацию

- Пометки **Правило** и принятые решения из спецификации становятся критериями реализации.
- Пометки **Предположение** нужно сохранить как открытые продуктовые решения и подтвердить до реализации зависимого поведения. До подтверждения можно выполнять независимую работу.
- Пометки **Проверить** — обязательные пункты T0, а не готовые требования.
- Раздел 12 спецификации задаёт исключения из объёма: для них не создавать задачи и не менять поведение.
- В документе ниже реализуется только план. Само наличие команд и текстов в исходной спецификации не означает запроса реализовать их сейчас.

## Текущее состояние репозитория

На момент составления плана активна `main`, синхронизированная с `origin/main`. В рабочем дереве есть незакоммиченные изменения, затрагивающие `.env.example`, `README.md` и код импорта/отчётов посещаемости. По содержимому они пересекаются как минимум с T3–T5 и историческими административными отчётами, которые спецификация явно исключает из своей области.

Эти изменения не включены в план как завершённая реализация и не перемещаются автоматически в новую ветку. До первой реализации нужно установить их происхождение, зафиксировать их отдельным коммитом/веткой или иным образом сохранить, затем начинать feature-ветки от актуальной `main`. Не сбрасывать и не переименовывать существующие ветки.

Предварительные наблюдения для T0:

- В `AttendanceDraftItemDTO` и `AttendanceRecord` есть `is_empty_time`; сервис подтверждения сейчас сохраняет пустое время как нулевую длительность. Удаление правила «N — 0 минут» затрагивает DTO, persistence, тексты и отчёты, а не только распознавание.
- В посещении уже есть связь с импортом, а сервис умеет получать фото импорта; доступ по новой кнопке всё равно требует отдельной проверки авторизации на каждом callback.
- В attendance-конфигурации есть `ATTENDANCE_TIMEZONE`; также есть отдельная настройка часового пояса для планировщика еженедельного leaderboard. T0 должен различить расчёт бизнес-периода и время запуска расписания.
- Есть незакоммиченные изменения по историческим административным отчётам. Проверить их пересечение с /report до ветвления; функциональность локального выбора месяца в `/report` не входит в спецификацию.
- Эти наблюдения не заменяют проверку всего списка из раздела 13 исходной спецификации.

## Правила ветвления

- `main` остаётся базой и получает изменения только через PR, согласно `CONTRIBUTING.md`.
- Использовать отдельную короткоживущую feature-ветку на каждый PR, с префиксом `codex/`.
- Каждую ветку создавать от актуальной `main` после включения её зависимостей. Не строить длинную цепочку веток от ещё не слитых feature-веток; зависимость оформлять порядком PR и при необходимости обновлять ветку от `main`.
- Указанные ниже имена — предлагаемые. Создавать конкретную ветку при начале соответствующей реализации, когда рабочая копия чиста или текущие изменения надёжно сохранены.
- Не создавать пустые ветки заранее. Сейчас ветки не создаются из-за существующих незакоммиченных изменений на `main`; сначала нужно сохранить и классифицировать эту работу.

### Порядок интеграции

1. Закрыть T0 и зафиксировать зависимости/открытые решения.
2. Слить T1, T2, T3 и T6 через отдельные PR. T3 включает T4/T5 последовательно, поскольку правила повторной даты и периода опираются на базовую семантику строк.
3. После базовых PR выполнять независимые T7, T8, T9 и T12–T14 с указанными зависимостями.
4. Реализовать T10, затем T11. Это самый крупный сценарий; держать интерфейс и изменение данных отдельными PR.
5. Перед завершением провести интеграционную проверку связанных сценариев импорта, фото-доступа, уведомлений, отчётов и ручного редактирования.

## Критерии готовности веток

- Каждая ветка закрывает только перечисленные задачи и критерии приёмки соответствующих разделов исходной спецификации.
- Логика размещена по слоям PyBot: handlers/dialogs — транспорт и UX, services — бизнес-операции и транзакции, repositories — persistence, DTO/domain — контракты и правила, DI — регистрация зависимостей.
- Для бизнес-логики обновлены целевые unit/integration tests; для команд и потоков — bot/flow tests, включая отказные сценарии. Для изменений модели/схемы проверены Alembic, репозитории, seed/bootstrap и deploy.
- Перед передачей каждой реализации выполнены целевые проверки и `just quality-gate`; локальный smoke-check добавляется для существенных пользовательских потоков, когда среда доступна.
- Обновлены только относящиеся к изменению пользовательские тексты и документация; новые ADR нужны только если меняется архитектурный контракт.
- PR проходит quality gates и review; `main` не меняется напрямую.

## Открытые предположения исходной спецификации

Подтвердить у владельца продукта до завершения зависимых частей. Самостоятельно превращать эти пункты в окончательные правила нельзя:

- T4: считать ли дату уже учтённой после удаления всех её посещений; спецификация предлагает считать навсегда учтённой.
- T1: при равенстве минут использовать соревнования с пропуском места (1, 2, 2, 4).
- T2/T14: при закрытии удалять сообщение, а если нельзя — убирать кнопки; сбрасывать ли ожидание ввода при новой команде.
- T8: максимум 10 месяцев на экране и постраничная навигация сверх лимита.
- T11: сортировка списка пользователей, размер страниц и сквозная нумерация; принимать ли час с одной цифрой; какой экран открывать после ручного добавления; обработка ручной записи при будущем фотоимпорте.
- T7/T11: поведение при сбое личного уведомления — сохранение остаётся успешным, ошибка только в логах.

  - `src/pybot/infrastructure/adapters/polza_vision_adapter.py:354-356`: `_parse_recognized_row` принудительно выставляет `is_empty_time = True`, если `time_raw in ("-", "—", "–", "нет", "прочерк")`.

  4. Сохранения столбца `is_empty_time` в схеме БД для обратной совместимости (без создания новых строк).

### 2. Определение «повторного импорта уже обработанной даты»
- Проверяется в `src/pybot/services/attendance_service.py:693`: `is_already_processed = await self._attendance_repo.is_date_processed(self._db, date_block.date)`.
- Реализовано в `src/pybot/infrastructure/attendance_repository.py:181-197`:
  ```python
  stmt = select(func.count()).select_from(AttendanceDate).where(AttendanceDate.date == visit_date)
  ```
- **Вывод:** Проверка идёт **НЕ по наличию посещений (`attendance_records`)** и **НЕ по статусу `attendance_imports`**, а по отдельной сущности **`AttendanceDate`** (таблица `attendance_dates`, где поле `date` уникально).
- Запись `AttendanceDate` создаётся в `save_confirmed_import` (`attendance_repository.py:235-240`) при подтверждении импорта.
- **Влияние на T4:** Если из даты будут удалены все `AttendanceRecord` через будущий `/edit_visits`, сама запись `AttendanceDate` останется в базе. В спецификации зафиксировано продуктовое предположение: считать дату навсегда учтённой. Текущая модель данных уже соответствует этому предположению.

### 3. Ограничение глубины прошлых дат
- **Где в коде:** `src/pybot/services/attendance_service.py:692-703`:
  ```python
  is_out_of_month = (date_block.date.year != current_year) or (date_block.date.month != current_month)
  if is_out_of_month:
      is_ignored = True
      ignore_reason = "прошлый месяц"
  ```
- При подтверждении (`attendance_service.py:388`): все блоки с `is_ignored=True` безусловно пропускаются (`skipped_dates_count += 1; continue`).
- **Вывод:** Ограничения именно в «1 месяц» в коде нет — код просто отклоняет **любую дату**, у которой год или месяц не равны текущему (`current_year`, `current_month`), присваивая метку `прошлый месяц`. При этом будущие даты обрабатываются так же некорректно (как «прошлый месяц»).
- **Влияние на T5:** Необходимо разделить валидацию:
  1. Будущие даты (`date > today` в часовом поясе Екатеринбурга) — строго отклонять с ошибкой.
  2. Любые прошлые даты (`date <= today`) — разрешать импорт, но помечать черновик предупреждением для администратора.

### 4. Расчёт места в /my_hours, /my_rank и /report, обработка равенства

    stmt = select(AttendanceRecord.user_id, total_minutes_col, visits_count_col)...
           order_by(total_minutes_col.desc(), AttendanceRecord.user_id.asc())

### 7. Хранение уровней и баллов (академические и репутационные)
- **Текущее хранение баллов:**
  - `src/pybot/db/models/user_module/user.py:59-60`: `academic_points: Mapped[int]` и `reputation_points: Mapped[int]` в таблице `users`.
  - При изменении баллов (`src/pybot/db/models/user_module/user.py:192-211`):

    То есть сейчас отрицательное списание **не отклоняется**, а принудительно обрезается до 0 (`max(..., 0)`).
- **Текущее хранение уровней:**
  - Таблица `levels` (`src/pybot/db/models/user_module/level.py:18-40`): `id`, `name`, `level_type` (`ACADEMIC`/`REPUTATION`), `required_points`.
  - Таблица `user_levels` (`src/pybot/db/models/user_module/user_level.py:15-24`): `user_id`, `level_id`, `UniqueConstraint("user_id", "level_id")`.
  - При изменении баллов (`src/pybot/services/points.py:64-70`):
    ```python
    actual_delta, new_score = user.change_user_points(...)
    new_level = self.level_calculator.calculate_level(new_score, all_levels)
    if new_level:
        user.change_user_level(new_level.id, dto.points.point_type)
    ```
  - `LevelCalculator.calculate_level` (`src/pybot/domain/services/level_calculator.py:20-33`) вычисляет уровень строго по текущему `current_points`.
- **КРИТИЧЕСКИЙ ВЫВОД ДЛЯ T12:**
  1. Уровень пользователя в текущей системе **понижается при списании баллов**, что прямо нарушает правило спецификации 9.2 («Уровень участника — несгораемый»).
  2. Понятия «максимальный достигнутый уровень» в БД нет. Запись в `user_levels` просто перезаписывается на меньший `level_id`.
  3. При списании больше баланса транзакция не реджектится, а баланс принудительно обнуляется, списывая остаток.
- **Влияние на T12:**
  - Валидация в `PointsService`: при списании больше текущего баланса — возбуждать доменное исключение с текстом («Недостаточно баллов для списания. Текущий баланс: X»), не выполняя транзакцию.
  - Обновление уровня: уровень должен обновляться **только вверх** (`new_level.required_points > current_level.required_points`).
  - Структура хранения: для сохранения истории/максимального уровня проверить необходимость явного поля/таблицы или фиксации инварианта обновления `UserLevel` только при превышении порога.
