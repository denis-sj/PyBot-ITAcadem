# Отчёт Stage C — конвейер эвалов агента

## Результат

Реестр, автопроверки, выборочные eval-команды и рецепт добавления инструмента готовы. Проверка инструмента `get_my_achievements` прошла. После исправления критерия smoke принимает не более одного промаха выбора инструмента при нуле ошибок безопасности. В исходных 19 кейсах был один безопасный отказ в security-кейсе без вызова `bot_capabilities`; он принимается как корректная альтернатива. Порог полного набора B3 остаётся прежним: не ниже 37/39 старых кейсов. Ошибочный STOP C4 снят; решение по объединению инструментов или выдаче схем по контексту не требуется.

## Конвейер C1–C5

- В `AgentToolRegistry` рядом с инструментом хранятся имя, разрешённые роли, тип (`read`/`action`), требование подтверждения, описание для модели и вызываемый сервис. Проверка роли повторяется при исполнении.
- Для всех 39 инструментов тесты требуют явные метаданные, описание до 60 токенов, подтверждение для действий, не менее двух разрешённых eval-кейсов и кейс отказа по роли/инъекции. Отдельно проверяется отказ каждого инструмента при вызове от роли без прав.
- Постоянный префикс измерен по ролям и сверяется с сохранёнными бюджетами. Во время полного B3 он составлял: Student 3 689 / 4 243 токена, Mentor 4 054 / 4 643, Admin 5 565 / 6 379. После уточнения описания места в инструменте текущий префикс: Student 3 689, Mentor 4 083, Admin 5 594 токена (86,94%, 87,94% и 87,69% бюджетов ролей). Все ниже порога STOP в 95%.
- Добавлены режимы `--tool`, `--smoke` и `--repeat`; B3 сравнивает полный ×3 с сохранённым эталоном из 39 старых кейсов. `--tool` и `--smoke` сами по себе не объявляют B3 принятым.
- Рецепт с карточкой идеи находится в `docs/agent/adding-a-tool.md`; короткая ссылка добавлена в `AGENTS.md`. README исправлен отдельным коммитом и описывает DeepSeek V4.1 Flash, `reasoning.effort=none` и маршрут Polza `decart/fp4` → `deepseek` с `allow_fallbacks=true`.
- Для C5 взят уже существующий инструмент достижений. Его бизнес-сервис не менялся: проверка использовала два позитивных кейса и один кейс отказа для нераспределённой роли. Для подключения фичи к единому реестру и eval-набору затронуты два feature-specific файла — `src/pybot/services/agent/tools.py` и `evals/agent/cases.json`; общие проверки реестра остаются в одном наборе тестов.

## Экранирование пользовательского текста

Добавлены и выполнены тесты с именем `<b>x</b> & <a href="tg://user?id=1">Аня</a>` и аналогичным текстом цели/стека:

- дайджест достижений HTML-экранирует имя; личное поздравление отправляется без parse mode;
- рекомендации «кто поможет» и ответы агента выводятся как обычный текст;
- подтверждение стека «Записал: …», ответы и напоминания о чекине, а также подтверждение цели отправляются без HTML-разбора;
- поле ссылки встречи не добавлялось.

Проверки находятся в `tests/services/test_community_achievement_service.py`, `tests/bot/test_community_checkin_handlers.py`, `tests/bot/test_technology_stack_registration.py` и `tests/agent/test_handlers.py`.

### Префикс и стоимость до Stage B

Сравнение использует сохранённый отчёт до функций сообщества (`baseline.json`) и текущий proxy tokenizer `cl100k_base`:

| Роль | До сообщества: инструкции + схемы | Сейчас: инструкции + схемы | Рост | Кандидатное сокращение описаний |
| --- | ---: | ---: | ---: | ---: |
| Student | 977 + 943 = 1 920 | 2 160 + 1 529 = 3 689 | +1 769 (+92,1%) | −51 → 3 638 |
| Mentor | 977 + 943 = 1 920 | 2 160 + 1 894 = 4 054 | +2 134 (+111,1%) | −61 → 3 993 |
| Admin | 977 + 2 398 = 3 375 | 2 160 + 3 405 = 5 565 | +2 190 (+64,9%) | −61 → 5 504 |

Инструкция сама выросла на 1 183 токена во всех ролях; новые схемы добавили 586 / 951 / 1 007 токенов соответственно. Кандидатные краткие описания (каждое не длиннее 30 токенов при лимите C2 ≤60) экономят лишь 51–61 токен на полный префикс роли: около 1,1–1,5% текущего префикса. Их можно применить после B, если важна такая экономия; это не нужно решать для запуска B.

Кандидатные формулировки: `get_meeting_attendees` — «Кто придёт на встречу; только создатель или Admin»; `get_my_achievements` — «Мои достижения и серия посещений»; `get_my_goal` — «Моя текущая цель и статус»; `get_my_technology_stack` — «Мой стек технологий и уровни владения»; `find_technology_helpers` — «Подобрать менторов и участников, которые помогут с технологией»; `get_upcoming_meetings` — «Ближайшие доступные встречи». Для действий: кратко оставить действие и требование подтверждения; для создания встречи сохранить подсказки `audience_kind='all'` и места без предлога. Наибольшая измеренная экономия всего 61 токен на роли Mentor/Admin, поэтому менять схемы до B не требуется.

Доля cached tokens в smoke — 86 016 / 110 444 = 77,88%. Короткий `--tool` прогон имел 21,83% кэша (3 кейса, 5 запросов); первый smoke-запрос содержал 3 369 prompt-токенов и 0 cached. Это указывает на холодный кэш коротких запусков как основную причину высокой средней Stage C: 0,62762180 ₽ / 22 вопроса = 0,0285283 ₽/вопрос. Сам smoke стоил 0,025637 ₽/вопрос, на 8,62% выше ориентира 0,0236028 ₽ и ниже установленного предела 0,02596308 ₽. В ответах Polza отдельный тариф для cache не наблюдался, поэтому точное рублёвое распределение между кэшированным и обычным вводом недоступно; дополнительных платных запросов для этой диагностики не делалось.

Эти результаты не дали ошибок выхода за права, неверного получателя, действия без подтверждения, нескольких действий на одно подтверждение или вызова запрещённого инструмента. В smoke два синтетических действия были исполнены только после симулированного подтверждения.

Runner берёт вопросы, роли, историю и ожидания из `cases.json`, отправляет запросы реальной модели и проходит через `AgentService`, реестр и политику подтверждений. Чтения и акторы синтетические; порт действий заменён mock-адаптером. Runner не подключает реальную БД, репозитории, production-сервисы или отправку в Telegram. Он отдельно считает исполнение до и после подтверждения.
